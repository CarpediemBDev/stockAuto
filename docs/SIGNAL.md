# 🚀 Market Scanner Signal Logic (SIGNAL)

본 문서는 [FILTER.md](file:///d:/dev/workspace/stockAuto/docs/FILTER.md)를 통해 선별된 주도주들을 대상으로, 실제 진입 및 이탈을 위한 정밀한 기술적 시그널 로직을 정의합니다.

---

## 1. 분석 타임프레임 (Multi-Timeframe)
*   **15분봉 (Trend)**: FILTER 조건을 유지하고 있는지 확인 (The Narrative)
*   **5분봉 (Momentum)**: 중간 추세 및 실시간 거래량 변화 확인 (The Confirmation)
*   **1분봉 (Execution)**: VWAP 및 Wick Ratio 기반 정밀 진입/이탈 타점 (The Entry)

---

## 2. 핵심 기술 지표 (Indicators)

| 지표명 | 영문명 | 설명 | 비고 |
| :--- | :--- | :--- | :--- |
| **VWAP** | Volume Weighted Average Price | 거래량 가중 평균가. 기관/세력의 평균 단가로 간주 | **필수** |
| **RVOL** | Relative Volume | 최근 20개 캔들 대비 현재 거래량의 비율 | **최소 2배 이상** |
| **Wick Ratio** | Candle Wick Ratio | 전체 캔들 길이 대비 윗꼬리의 비율 | **30% 미만 권장** |
| **RSI** | Relative Strength Index | 과매수/과매도 지표 | 15분봉 50 이상 필수 |
| **MACD** | Moving Average Conv. Div. | 추세의 방향과 강도 측정 | 골든크로스 확인용 |

---

## 3. 매수 시그널 조건 (Entry Rules)

다음 모든 조건이 **동시에 만족(AND)**될 때 진입합니다.

### Step 1: 대세 확인 (15분봉)
- [ ] **RSI(15m)** > 50 (우상향 추세)
- [ ] **Price** > MA20(15m) (추세 유지)

### Step 2: 기회 포착 (5분/1분봉)
- [ ] **RVOL** > 2.0 (평소보다 2배 이상의 거래량 동반)
- [ ] **Price** > **VWAP** (세력의 단가보다 높은 위치)
- [ ] **MACD Histogram** > 0 (상승 모멘텀 지속)

### Step 3: 최종 필터 (Candle Shape)
- [ ] **Wick Ratio** < 30% (매도세보다 매수세가 압도적임)
- [ ] **Price** > 전일 고가 혹은 당일 시가 (주요 저항선 돌파)

---

## 4. 가짜 돌파 방지 및 위험 알림 (False Breakout Filter)

아무리 가격이 올라도 아래 조건에 해당하면 **'매수 금지'** 혹은 **'탈출'** 시그널을 보냅니다.

*   **위험 1 (Wick Trap)**: 거래량은 터졌으나 윗꼬리가 전체 캔들의 50% 이상일 때 (Pump & Dump 주의)
*   **위험 2 (VWAP Fade)**: 급등 후 주가가 VWAP 아래로 하향 돌파할 때 (세력이 털고 나간 신호)
*   **위험 3 (Divergence)**: 가격은 신고가를 경신하지만, 거래량이나 RSI는 낮아질 때 (힘의 소진)

---

## 5. 사례 분석: 드림랜드(TDIC)
*   **급등기 (5/12~13)**: 15분봉 RSI 70 돌파, RVOL 10배 이상, VWAP 위에서 안정적 흐름 유지.
*   **급락기**: 장중 윗꼬리 60% 이상 발생 및 VWAP 하향 돌파 시점이 최종 매도 타점.

## 6. 라이브 신호 필드 계약 (Live Signal Field Contract)

### 6.1 왜 계약인가

전략 클래스(`backend/app/strategies/*`)는 **백테스트 엔진**(`backend/app/backtests/backtest_engine.py`)이 생산하는 지표 이름으로 작성돼 있다. 라이브 스캐너가 같은 값을 다른 이름으로 실으면 `BaseStrategy._safe_get`이 예외 없이 기본값 `0`을 돌려주고, 전략은 **에러 한 줄 없이 "진입 조건 미충족"으로 퇴화**한다.

이 침묵 실패는 로그에도 남지 않아 "오늘은 살 종목이 없네"와 구분되지 않는다. 실제로 2026-08-23 실측에서 전략 95종 중 **74종이 라이브에서 영구 미진입** 상태였다. 대표 사례가 챔피언십 대형주 3년 부문 우승 전략인 `cross_sectional_momentum`으로, 필요한 값을 스캐너가 이미 계산해 두고도 신호에 싣지 않아 단 한 번도 진입하지 못했다.

> **원칙: 라이브 신호 딕셔너리는 백테스트 엔진과 동일한 필드명을 사용한다.**
> 이름이 갈리는 순간 백테스트 성적은 라이브로 전이되지 않는다.

### 6.2 계약의 소유자

`backend/app/scanner/signal_contract.py`가 표준 필드명과 계산식을 **단독으로 소유**한다. 스캐너의 두 신호 생산 지점(전체 스캔 = 진입 채점, 단일 종목 전용 분석 = 청산 채점)이 이 모듈을 공통으로 사용한다. 필드를 추가할 때 스캐너 쪽에 직접 키를 적지 말고 반드시 이 모듈을 고친다.

| 표준 필드 | 의미 | 라이브 산출 기준 |
| :--- | :--- | :--- |
| `Open` | 당일 장 시작가 | 5분봉의 **마지막 거래일 첫 봉**(5거래일치가 담기므로 `iloc[0]` 금지) |
| `gap_pct` | 시가 갭 비율 | 스캐너 후보값 통과 |
| `Wick` | 윗꼬리 비율 | `detect_fakeout_risk` 산출값 |
| `change_pct` | 20봉 절대 모멘텀 | **일봉 20일** 수익률 |
| `relative_strength` | QQQ 대비 초과강도 | 종목·지수 **모두 일봉 1년** 누적 수익률의 차 |
| `dist_to_high` | 52주 고가 이격(%) | **일봉 전 구간 최고가**(당일 봉 제외) 대비 |
| `is_penny` | 저가주 여부 | 종가 `<= $10.00` (백테스트 기준과 동일) |
| `is_triple_ema_up` | EMA 9>20>120 정배열 | **일봉으로 통일**하여 산출 |

### 6.3 시간축 함정 (Timeframe Trap)

백테스트는 모든 지표가 **하나의 인터벌**에서 나오지만, 라이브는 15분봉·5분봉·일봉이 섞인다. 같은 이름이라도 시간축이 다르면 의미가 뒤집힌다.

*   `change_pct`를 라이브 주 프레임(15분봉) 20봉으로 계산하면 약 5시간짜리 초단기 신호가 되어 '모멘텀'이 아니라 고점 추격이 된다. 그래서 일봉 20일로 계산한다.
*   `EMA9`/`EMA20`은 15분봉, `EMA120`은 일봉에서 산출되므로 셋을 그대로 비교하면 상승 추세에서 조건이 사실상 항상 참이 된다. 그래서 정배열 판정만 일봉으로 통일한다.
*   `dist_to_high`는 스캐너 1단계가 **15분봉 5거래일 고점** 기준으로 계산해 왔다. 백테스트는 누적 최고가 기준이므로, 라이브에서만 "고점 근접"이 쉽게 참이 되어 백테스트보다 **헐겁게 진입**했다(`strategy_a`·`strategy_c`는 -1.5% 기준 +20점, `cross_sectional_momentum`은 -5% 기준 +10점). 같은 신호 안의 `is_near_52w_high`는 이미 일봉 최고가를 쓰고 있어 '고점'의 정의가 둘로 갈려 있었다. 일봉 기준으로 통일했다.
*   `relative_strength`는 **종목 15분봉 5거래일 수익률에서 지수 15분봉 10거래일 수익률을 뺐다.** 두 항의 구간이 달라 그 자체로 틀린 뺄셈이며, 상승장에서 지수 10일 수익률이 5일보다 크므로 초과강도가 체계적으로 과소평가됐다. 지수 일봉 조회(`fetch_index_daily`)를 추가해 두 항을 같은 일봉 구간으로 맞췄다.

> 두 필드는 `details`가 아니라 **`cand` 단계에서** 덮어쓴다. 스캐너 자체 채점([scanner.py](../backend/app/scanner/scanner.py)의 `calculate_strategy_score`)과 스케줄러 채점이 같은 값을 보게 하기 위해서다. 데이터가 부족하면 헐거운 15분봉 값으로 되돌아가지 않고 보수적 기본값(`-100.0` / `0.0`)을 쓴다.

### 6.4 상시 가드 (`check_signal_field_contract.py`)

`verify_harness`의 [2/8] 위험 검사 단계가 매번 이 가드를 돌린다. 앱을 import하지 않고 AST로만 대조하므로 `.env`나 DB 없이도 동작한다.

전략이 읽는 모든 필드는 반드시 셋 중 하나로 분류돼 있어야 하며, 어디에도 없으면 **새 드리프트로 간주해 반려**한다.

| 분류 | 뜻 | 선언 위치 |
| :--- | :--- | :--- |
| `LIVE_SIGNAL_KEYS` | 라이브가 실제로 싣는 필드 | `signal_contract.py` |
| `UNSUPPORTED_LIVE_FIELDS` | 외부 데이터가 없어 **원리상 불가** | 사유별 그룹 |
| `PENDING_LIVE_FIELDS` | 계산은 가능하나 **아직 미구현**(백로그) | 사유별 그룹 |

가드가 잡는 위반은 네 가지다.

1. 스캐너가 싣는 키가 `LIVE_SIGNAL_KEYS` 선언에 없음 (선언이 현실과 어긋남)
2. 선언에는 있는데 스캐너가 싣지 않음 (거짓 선언)
3. 전략이 읽는 필드가 세 집합 어디에도 없음 (새 드리프트)
4. 이미 라이브에 실리는데 결손으로 남은 선언, 또는 아무도 읽지 않는 사문화된 선언

> 가드가 실제로 반려하는지는 네거티브 컨트롤 6종으로 검증했다(선언 삭제·미분류 필드 추가·노후 선언·사문화 선언·표준 필드 병합 제거·기준선). 통과만 보고 동작한다고 믿지 않는다.

### 6.5 남은 결손

1차 정정 후에도 **71종이 여전히 라이브 미진입**이다. 가드 기준으로 미구현 85개 필드(`PENDING`), 원리상 불가 32개 필드(`UNSUPPORTED`)가 남아 있고, 라이브 미지원 필드에 의존하는 전략은 79종이다.

`UNSUPPORTED`에만 의존하는 전략은 **카탈로그에서 선택 불가로 막아야 한다.** 현재는 선택은 되는데 실제로는 아무것도 매수하지 않는다.
