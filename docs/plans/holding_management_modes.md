# 보유 종목 관리 모드 (격리 · 수확 · 방어 · 위임)

> 소유 주제: **봇이 매수하지 않은 보유 종목**을 봇이 어떻게 다룰 것인가에 대한 설계 정본.
> 상태: 설계 확정(2026-09-06). **1~5단계 구현 완료(2026-09-06)**, 6단계 미착수.
> 관련: [SIGNAL.md](../SIGNAL.md) (매도 신호 정의), [SCHEMA.md](../SCHEMA.md), [API_STANDARD.md](../API_STANDARD.md)

## 1. 배경

2026-09-05 현황판에서 admin 계정에 HCTI 실계좌 매수 이력 11건을 수동 이관하고 손절 로직을 실측했다. 그 현황판의 "미해결 위험"이 예측한 대로, 평가손익 -47.5%인 보유분이 다음 사이클에서 stop_loss 판정에 걸려 즉시 매도됐다.

이것은 버그가 아니라 **설계 공백**이다. 현재 코드에는 "봇이 사지 않은 종목"이라는 개념이 없다.

실증권 API를 붙이면 이 공백이 그대로 사고가 된다. `sync_broker_holdings`는 DB에 없는 브로커 보유분을 "유령 보유(Phantom holding)"로 간주해 `ctx.first_slot_key`(첫 번째 전략 슬롯) 아래에 Holding을 자동 생성한다. 즉 **사용자가 봇 도입 이전에 직접 매수한 종목 전체가 자동으로 봇 관리 대상이 되고**, 시그널이 나쁘면 그대로 청산된다. 현재 기본값이 "봇이 건드린다"인 것이 문제의 뿌리다.

## 2. 왜 단순 보호 플래그도, 단순 손절도 답이 아닌가

### 2.1 보호 플래그만 다는 안 (기각)

`is_protected` 하나로 매도를 막으면 계좌에 좀비 포지션이 영구히 쌓인다. 그 평가액은 슬롯 자본에 계속 잡히고(`calculate_slots_allocation`), 봇 성과와 실제 계좌 성과는 영원히 어긋난다.

### 2.2 규칙대로 손절하는 안 (기각)

현재 구현에서 이것은 "규칙 적용"이 아니라 **기준점 오염으로 인한 자동 덤핑**이다.

- `get_stop_loss_pct`는 최소 3.0% + ATR x 1.5다. 봇이 방금 진입한 포지션을 전제로 한 값이다.
- 외부 유입 포지션의 `avg_price`는 몇 달 전 매수가다. -20%에 물려 있으면 첫 사이클에 무조건 참이다.
- 판단이 개입할 여지가 0이다. 봇이 그 종목을 처음 본 순간이 곧 청산 시점이 된다.

참고로 트레일링 스탑과 롤링 박스 스탑은 `highest_price > avg_price` 가드 덕에 이 상황에서 발동하지 않는다(`trade_calculations.py`). 즉 **가드가 한 군데만 있고 나머지엔 없는 비대칭 상태**다.

### 2.3 채택안: 관할권 분리 (Jurisdiction Split)

> **봇이 사지 않은 포지션은 봇의 관할이 아니다. 관할로 넘기는 것은 사용자의 명시적 행위이고, 넘어오는 순간 그 포지션은 "새로 진입한 것"으로 취급한다.**

## 3. 사용자 관점 모델

종목별 설정이며 웹·모바일이 같은 값을 본다. 언제든 올리고 내릴 수 있다.

```
  (o) 맡기지 않음                          <- 기본값 (= 격리)
        봇이 아무것도 하지 않습니다

  ( ) 부분적으로 맡김
        [ ] 급등하면 수확
        [ ] 무너지면 알림

  ( ) 봇에 전부 맡김
        봇이 산 종목과 동일하게 관리합니다
```

- 격리는 사용자가 선택하는 것이 아니라 **자동 판정**이다. 봇이 사지 않은 종목은 자동으로 격리에서 시작한다.
- "부분적으로 맡김"을 고르면 체크박스 최소 1개는 켜야 한다.
- **봇이 직접 산 종목에는 이 선택지가 뜨지 않는다.** "봇 관리 중" 고정 표시. 봇이 자기 규칙으로 산 것을 중간에 규칙에서 빼면 2.1의 좀비 포지션 문제가 그대로 재발한다.

### 모드별 봇 동작

| 모드 | 급등 시 | 하락 시 | 추가매수 | 슬롯 자본 산입 |
| :--- | :--- | :--- | :--- | :--- |
| 맡기지 않음 | - | - | - | 제외 |
| 수확만 | 꺾이면 매도 | - | - | 제외 |
| 알림만 | - | 경보 전송 | - | 제외 |
| 수확 + 알림 | 꺾이면 매도 | 경보 전송 | - | 제외 |
| 전부 맡김 | 봇 규칙대로 | 봇 규칙대로 매도 | 허용 | 산입 |

추가매수(물타기)는 "전부 맡김"에서만 일어난다. 중간 단계에서는 절대 종목을 더 사지 않는다.

| 컬럼 | 타입 | 용도 | 도입 단계 |
| :--- | :--- | :--- | :--- |
| management | String, not null, default "BOT_OWNED" | BOT_OWNED / EXTERNAL / DELEGATED | 1 |
| observed_base_price | Numeric(20,4), nullable | 봇이 이 종목을 처음 본 가격. 수확의 기준 앵커 | 3 |
| harvest_enabled | Boolean, default False | 수확 모드 opt-in | 3 |
| harvest_armed | Boolean, default False | 급등 무장 여부 | 3 |
| guard_enabled | Boolean, default False | 방어 경보 opt-in | 4 |
| guard_baseline_score | Float, nullable | 방어 켠 시점의 시그널 점수 | 4 |
| guard_baseline_low | Numeric(20,4), nullable | 방어 켠 이후 관측 저가(단조 하향 래칫) | 4 |
| risk_basis_price | Numeric(20,4), nullable | 위임 시점가. 손절 계산 앵커 | 6 |

### 4.1 risk_basis_price를 avg_price와 분리하는 이유

`avg_price`는 현재 두 가지 일을 동시에 하고 있다.

| 용도 | 사용처 | 위임 시 필요한 값 |
| :--- | :--- | :--- |
| 실현손익 계산 | TradeLog.realized_pnl, return_rate | 실제 매수가 (건드리면 손익이 거짓이 된다) |
| 손절선 기준 | calculate_profit_rate -> check_stop_loss_breach | 위임 시점가 (과거 손실이 청산을 강탈하면 안 된다) |

위임 시 `avg_price`를 현재가로 덮어쓰면 손절은 정상화되지만 실현손익이 조작된다. 그래서 **리스크 기준가만 분리**한다. NULL이면 `avg_price`로 폴백하므로 기존 BOT_OWNED 레코드는 그대로 동작한다.

`management`를 bool이 아닌 String enum으로 파는 이유는, DELEGATED를 나중에 추가할 때 마이그레이션을 두 번 하지 않기 위해서다.

2단계가 선행 과제로 들어간 이유는 8절 참조.

### 5.1 1단계 - 격리: 막아야 할 지점 6곳

"안 건드린다"는 무행동이 아니다. 현재 기본값이 "건드린다"이므로 능동적으로 막아야 한다.

| # | 지점 | 안 막으면 |
| :--- | :--- | :--- |
| 1 | scheduler.sync_broker_holdings (유령 보유 복원) | 애초에 EXTERNAL로 태어나지 않는다. 여기가 뿌리 |
| 2 | scheduler.process_exit_signals (매도 판정) | 손절·시그널붕괴 매도가 그대로 나간다 |
| 3 | scheduler 매수 경로 (중복 조회) | 조회가 strategy_type 단위라 같은 티커를 다른 슬롯에서 또 산다 |
| 4 | multi_strategy_manager.calculate_slots_allocation | 미매핑 전략 폴백 때문에 첫 슬롯 매수여력이 깎인다 |
| 5 | scheduler.sync_broker_holdings (수량 차분 배분) | 사용자의 계좌 밖 매도가 봇 슬라이스에서 차감된다 |
| 6 | router_account 의 force-liquidate | 전량 청산에 외부 보유가 섞여 들어간다 |

**2번은 배제가 아니라 분기여야 한다.** 관측과 highest_price 갱신은 공통으로 돌리고, 그 아래 손절·시그널붕괴 블록만 조건부로 감싼다. exit 루프 상단에서 continue 하면 3단계 수확 모드가 눈이 먼다.

**5번 배분 순서를 명시한다.** 현재는 증가분을 `db_hs[0]`(순서 미보장)에, 감소분을 리스트 순회 순서로 차감한다.

- 증가 -> EXTERNAL 행에 가산 (사용자가 앱 밖에서 산 것). 없으면 생성
- 감소 -> EXTERNAL -> DELEGATED -> BOT_OWNED 순으로 차감

계좌에서 사라진 종목의 레코드 삭제(sweep)와 수량 동기화는 EXTERNAL에도 계속 적용한다. 매도를 안 하는 것과 존재를 무시하는 것은 다르다.

평가금 표시는 별도 조치가 필요 없다. `_refresh_stale_holding_prices`가 전략 필터 없이 전 종목의 last_price를 갱신하므로 EXTERNAL 평가금이 동결되지 않는다.

### 5.2 3단계 - 수확 판정 규격

숫자가 두 개 쓰이며 역할이 다르다.

| | 역할 | 매도 |
| :--- | :--- | :--- |
| 무장 (+X%) | 감시를 시작하는 조건 | 안 함 |
| 트레일링 (고점 -Y%) | 실제 매도 조건 | 함 |

동작:

1. **무장**: `current > observed_base_price * (1 + X)`. X는 ATR 기반 동적. 무장 시점에 `highest_price`를 그 시점 가격으로 리셋하고 거기서부터 추적한다.
2. **추적**: 1분 사이클마다 `highest_price` 갱신(단조 증가). 고점을 판단하지 않고 기록만 한다.
3. **매도**: `current <= highest_price * (1 - Y)`. 노이즈 버퍼는 관측 횟수 2회와 실제 경과 2분을 모두 요구한다 — 사이클 수만 쓰면 주기 변동(실측 104~846초)에 따라 대기 시간이 함께 흔들린다. 이탈 시각은 컬럼(`harvest_breach_started_at`)에 두어 재기동이 대기를 0으로 되돌리지 못하게 한다.
4. **하한 가드**: `current > observed_base_price` 일 때만 매도 허용. **관측 시작가 아래에서는 절대 팔지 않는다.**

트레일링 앵커를 `avg_price`가 아니라 `observed_base_price`로 바꾸는 것이 핵심이다. 기존 `check_trailing_stop_breach`의 `highest_price > avg_price` 가드는 반토막 종목에서 영원히 거짓이므로 수확이 발동할 수 없다. **헬퍼 시그니처는 건드리지 않고 호출부에서 앵커만 교체한다** — 백테스트 경로와 함수 계약이 갈라지지 않게 하기 위해서다.

**확정된 파라미터 (2026-09-06 사용자 승인, `trade_calculations.py` 상수)**

| 값 | 공식 | 예시 |
| :--- | :--- | :--- |
| 무장 임계 X | `min(40%, max(15%, ATR% x 4.0))` | ATR 2% → 15%, ATR 5% → 20%, ATR 15%+ → 40%(상한) |
| 트레일링 Y | `max(5%, ATR% x 2.0)` | ATR 2% → 5%, ATR 10% → 20% |

Y는 기존 `get_trailing_stop_pct`(`max(2.0%, ATR x 1.0)`)보다 넓다. 급등 종목은 눌림이 깊어 좁은 폭이면 상승 도중에 털리고, 봇이 진입 근거를 갖지 않은 포지션이라 조기 청산의 기회비용이 봇 소유 포지션보다 크기 때문이다. 무장 임계에 상한을 두는 이유는 초고변동성 종목에서 임계가 발산해 기능이 사실상 꺼지는 것을 막기 위함이다. 수확은 전량 매도이며 부분 수확은 채택하지 않았다.

**수확 모드는 절대 고점에서 팔지 않는다.** 구조적으로 항상 고점 -Y%에 판다. 그것이 "언제 꺾일지 예측하지 않아도 되는" 대가다.

무장 시점 텔레그램/푸시 알림을 함께 넣는다. 사용자가 자는 동안 팔리는 것이 이 기능의 전제이므로, 아침에 맥락이 남아 있어야 한다.

### 5.3 4단계 - 방어 경보 판정 규격

**전략과 분리한다.** `is_signal_collapsed`의 판정선은 전략마다 다르고(기본 40/50점, 전략 A 40점, 크로스섹셔널 모멘텀 20점), `calculate_score` 산식 자체도 전략마다 다르다. 외부 보유 종목은 어떤 전략으로도 진입한 적이 없으므로 특정 전략의 잣대를 들이댈 근거가 없고, 사용자가 전략을 바꿨다고 기존 보유 종목의 경보 기준이 흔들려서도 안 된다.

**절대 점수선을 쓰지 않는다.** 이것이 이 설계에서 가장 큰 함정이다. -50% 물린 종목은 십중팔구 이미 점수가 40 미만이므로, 절대선을 쓰면 방어를 켜는 순간 즉시 경보가 되어 2.2의 즉시 덤핑이 이름만 바꿔 재현된다. 상태(state)가 아니라 **전이(transition)**를 봐야 한다.

발동 조건 (둘 다 만족):

1. `current_score < guard_baseline_score - delta` — 켤 때보다 추가로 악화
2. `current_price < guard_baseline_low` — 켠 이후 신저가 갱신

`guard_baseline_low` 래칫은 `compute_rolling_box_stop`의 단조 증가 불변식을 방향만 뒤집은 `compute_guard_low`다.

**확정된 파라미터 (2026-09-06 구현, `trade_calculations.py` 상수)**

| 값 | 상수 | 설명 |
| :--- | :--- | :--- |
| 점수 악화 임계 | `GUARD_SCORE_DROP_DELTA = 15.0` | 기준선 대비 이만큼 더 떨어져야 "추가 악화" |
| 유예기간 | `GUARD_GRACE_MINUTES = 30` | 켠 직후 오발동 차단 |
| 경보 쿨다운 | `GUARD_ALERT_COOLDOWN_HOURS = 6` | 1분 사이클마다 반복 발송 차단 |

유예기간과 쿨다운의 기준 시각은 인메모리 캐시가 아니라 `guard_enabled_at`·`guard_last_alert_at` 컬럼이다. 재기동 후에도 유지되어야 하기 때문이다.

**고정 평가자는 `regime_switching`이다.** 점수가 절대값이 아니라 켠 시점 대비 변화량으로만 쓰이므로 평가자 선택이 판정을 좌우하지는 않지만, 기준이 중간에 바뀌면 변화량 자체가 무의미해지므로 고정이 필요하다. 사용자가 전략을 바꿔도 외부 보유 경보 기준은 흔들리지 않는다.

4단계는 **텔레그램/푸시 경보만 보내고 주문을 내지 않는다.**

### 5.4 5단계 - 방어 조치 (섀도 · 부분 청산)

수확과 방어는 위험의 성격이 다르다.

| | 수확 | 방어 |
| :--- | :--- | :--- |
| 최악의 결과 | 더 벌 수 있었음 | 손실 확정 후 반등 |
| 되돌릴 수 있나 | 기회비용뿐 | 불가. 실현 손실 + 세금 이벤트 |

또한 [strategy_alpha_verdict.md](../strategy_alpha_verdict.md)의 결론대로 이 프로젝트는 능동 타이밍 초과 알파를 확인하지 못했다. 하방 예측이라고 다를 이유가 없다. -90%로 가는 진짜 원인(상장폐지, 감사의견 거절, 임상 실패, 유상증자)은 기술적 지표가 늦게 반영하거나 갭 하락 한 방으로 반영한다.

#### 당초 판단과 그 정정 (2026-09-06)

당초에는 "4단계 경보를 수 주간 운영해 실측한 뒤 착수 여부를 정한다"로 미뤄뒀다. 그 판단을 정정했다.

정정 사유는 두 가지다.

첫째, **증거 부족은 기본값과 가드를 어떻게 잡을지의 근거이지 기능을 만들지 말라는 근거가 아니다.** 켤지 말지는 사용자가 정하고, 구현은 정확해야 하며 모르는 것은 모른다고 표시하면 된다. 실제로 3단계 수확도 검증되지 않은 ATR 파라미터로 구현했다. 위 표의 비대칭(기회비용 vs 실현손실)은 더 엄격한 가드의 근거였지 착수 금지의 근거가 아니었다.

둘째, **"수 주간 실측" 계획 자체가 순환이었다.** 그 실측은 사람이 경보 로그를 눈으로 보고 이후 주가와 상관분석하는 것이었는데, 그것이야말로 코드가 할 일이다. SHADOW 모드를 이 단계 안에 넣으면 착수 근거를 이 기능이 스스로 만들어낸다.

#### 3-모드

| guard_action | 동작 | 주문 |
| :--- | :--- | :--- |
| ALERT_ONLY (기본) | 알림만. 4단계와 동일 | 없음 |
| SHADOW | "팔았다면 이랬을 것"을 구조화 로그로 기록 | 없음 |
| LIQUIDATE | guard_sell_ratio 비율만큼 부분 청산 | 있음 |

#### 가드 5겹

조치의 최악은 되돌릴 수 없는 손실 확정이므로 경보보다 훨씬 보수적이어야 한다.

1. **종목별 opt-in에 기본 ALERT_ONLY** - 청산은 사용자가 명시적으로 켠다
2. **부분 청산 (기본 50%)** - 포지션 전체를 확정하지 않는다
3. **연속 충족 10사이클** (`GUARD_SUSTAIN_CYCLES`) - 수확의 2사이클보다 훨씬 엄격하다. 짧게 스친 붕괴로는 팔지 않는다
4. **보유분당 24시간 1회** (`GUARD_ACTION_COOLDOWN_HOURS`) - 무너지는 날 반복 청산하지 않는다
5. **활성화 시 고지** - "이 신호가 실제 붕괴를 예측한다는 근거는 아직 없다"를 UI에 명시한다

연속 충족 카운터(`guard_streak`)는 인메모리가 아니라 컬럼이다. 되돌릴 수 없는 청산의 누적 조건이 재기동으로 리셋되면 안 되고, 반대로 끊겼다 이어진 것을 연속으로 오인해도 안 된다. 모드를 바꿀 때도 리셋한다 - 알림만으로 쌓인 연속 충족이 청산 모드 전환 즉시 임계를 넘기면 사용자가 켠 직후 바로 팔린다.

#### SHADOW 로그 형식 (측정 원천)

```
[Guard][SHADOW] {ticker} would_sell_qty={n} price={p} score={s}
                baseline_score={bs} baseline_low={bl} streak={k} | no order placed
```

`ActionLog`에 WARNING 등급으로 쌓인다. 이후 가격 이력과 대조해 "경보가 실제 붕괴 전에 울렸는가"를 판정한다. 전용 테이블을 두지 않은 것은 의도적인 최소 구현이며, 분석 수요가 확인되면 그때 승격한다.

#### 판정과 집행의 분리

`_evaluate_guard`는 청산이 필요하다고 판단해도 직접 주문을 내지 않고 Part B 인자만 반환한다. 판정 로직 안에 되돌릴 수 없는 주문이 숨으면 안 되기 때문이다. 부분 수량은 Part B의 `sell_qty` 파라미터로 전달되며, 이 값이 None인 기존 모든 경로는 전량 매도로 동작한다.

### 5.5 6단계 - 위임 시 동작

1. `risk_basis_price = highest_price = 위임 시점가`, `buy_stage = 3`(추가매수 봉인), `strategy_type = 사용자가 고른 슬롯`, `management = DELEGATED`.
2. **재진입 심사 1회**: 기존 진입 게이트를 그대로 재사용한다 (`calculate_score(..., is_entry=True)` vs `get_cutoff_score(regime)`).
3. 결과를 통보한다. 미달이면 "봇 기준으로는 지금 새로 살 종목이 아니다"를 명시한다.
4. **위임 시점에 즉시 청산하지 않는다.** 청산은 다음 사이클의 정상 규칙에 맡긴다. 위임 버튼이 곧 매도 버튼이 되면 아무도 누르지 않는다.

`DELEGATED -> BOT_OWNED` 승격은 없다. 성과 원장을 분리하기 위해 끝까지 구분한다.

## 6. 백로그 — 고점 판단 방법론 재검토

> **미착수. 수확 모드(3단계) 구현 전 또는 직후에 별도 과제로 진행한다.**

현재 수확 모드가 채택한 "관측 최고가 기록 + 고정 비율 트레일링"은 가장 단순한 방식이며, 다음과 같은 구조적 한계가 있다.

- 절대 고점에서 팔 수 없고 항상 Y%를 반납한다
- 1분 사이클 사이의 급등락을 놓친다
- 고점의 "구조적 의미"(직전 스윙 하이, 저항선)를 전혀 보지 않는다

기술적 분석에는 고점을 판정하는 여러 방법론이 존재하며, 그중 일부는 관측 최고가보다 나은 청산 기준을 줄 수 있다. 검토 대상:

| 방법론 | 개요 | 검토 포인트 |
| :--- | :--- | :--- |
| 이동평균 이탈 (20일/50일선) | 종가가 이평선 아래로 이탈하면 추세 종료로 간주 | 급등 후 눌림에 관대. 대신 반응이 느려 반납분이 큼 |
| 직전 스윙 하이/로우 | 직전 고점 돌파 여부와 고점 갱신 실패(lower high)로 판정 | 구조적 의미가 명확. 스윙 판정 파라미터 민감도 확인 필요 |
| 도치안 채널 (Donchian) | N봉 최고/최저 채널 이탈 | 이미 유사 구현이 롤링 박스 스탑에 있음(compute_box_low). 재사용 가능 |
| ZigZag / 프랙탈 | 임계 변동폭 이상의 전환점만 고점으로 인정 | 후행 지표(repaint) 위험. 라이브 적용 시 착시 주의 |
| 피벗 포인트 / 저항선 | 전일 고저종 기반 저항 레벨 | 일봉 기반이라 분 단위 급등에 부적합할 수 있음 |
| 파라볼릭 SAR | 가속 계수 기반 추적 스탑 | 급등장에서 트레일링보다 타이트해 조기 청산 우려 |
| ATR 채널 (Chandelier Exit) | 최고가 - ATR x k | 현재 방식의 자연스러운 확장. 가장 먼저 비교해볼 후보 |
| 거래량 프로파일 | 거래량 급감으로 매수세 소진 판정 | 데이터 파이프라인에 거래량 시계열 확보 여부 확인 필요 |

**저장소 내 기존 자산**: 롤링 박스 스탑(`compute_box_low`, `compute_rolling_box_stop`, `check_rolling_box_breach`)이 이미 도치안 채널에 준하는 구현이며, 래칫 불변식과 백테스트/라이브 박스 길이 환산 로직까지 갖추고 있다. 신규 구현 전에 이것부터 수확 모드에 적용 가능한지 평가한다.

**검토 방법**: 신규 로직을 라이브에 바로 넣지 않는다. 과거 급등 사례(반토막 후 급등 종목)를 표본으로 뽑아 각 방법론의 청산가를 백테스트로 비교하고, 관측 최고가 트레일링 대비 개선폭이 실재하는지 먼저 확인한다. [strategy_alpha_verdict.md](../strategy_alpha_verdict.md)의 교훈대로, 원시 수익률이 아니라 동일 조건 대비 개선분으로 판정한다.

## 7. 알려진 한계

**브로커 물량은 물리적으로 하나다.** DB에서 EXTERNAL 10주 / DELEGATED 5주로 나눠도 증권사 계좌에는 15주 한 덩어리다. 봇이 5주를 팔면 증권사는 자기 원가 규칙(FIFO/평균)으로 실현손익과 세금을 계산한다. **이것은 회계·의사결정 격리이지 세무 격리가 아니다.** 세금이 걸리는 계좌라면 봇 계좌를 물리적으로 분리하는 것이 정답이고 이 기능은 차선이다.

**갭 하락은 방어할 수 없다.** 트레일링 스탑이 구조적으로 못 막는 구간이며 증권사 예약매도도 동일하다.

**유동성.** 급등 종목과 붕괴 종목 모두 시장가 청산 시 슬리피지가 크다. 백테스트 수치와 실체결이 가장 크게 벌어지는 구간이다. 지정가·분할 청산은 별도 과제로 남긴다.

**노이즈 버퍼 2사이클(약 2분).** 급락 국면에서는 반납분이 되지만, 빼면 순간 꼬리에 털린다. 실측 전에는 기존 설정을 유지한다.

## 8. 선행 과제 — 개별 종목 수동 매도가 없다

1단계 격리의 계약은 "봇이 안 건드림 = 사용자가 직접 관리"인데, **앱 안에 직접 관리할 수단이 없다.**

| 경로 | 상태 |
| :--- | :--- |
| REST force-liquidate | 전량 청산만. 종목 지정 불가 |
| MCP command (SELL) | 화이트리스트에는 있으나 501 반환. 실행 워커가 저장소에 존재한 적 없음 |

방어 경보(4단계)는 이것 없이는 "알림 받고 증권사 앱을 따로 켜세요"가 되어 반쪽이 된다. 그래서 개별 종목 수동 매도를 2단계 선행 과제로 배치한다.

구현 시 지킬 조건은 `app/mcp/router.py` 주석이 이미 규정하고 있다.

- user_id는 요청 본문이 아니라 인증 세션에서만 도출한다 (크로스유저 주문 주입 차단)
- 파괴적 명령은 confirm 게이트 없이 실행하지 않고 dry-run 프리뷰를 먼저 준다
- 자동 스캐너 봇과의 경합을 막기 위해 주문 락(`app/core/locks.py`)을 경유한다

MCP 실행 워커 복원은 별개 과제로 남긴다. REST 개별 매도가 더 단순하고 먼저다.

### 8.1 구현 결과 (2026-09-06)

`POST /api/v1/account/holdings/{ticker}/sell`로 구현했다. 계약 상세는 `API_STANDARD.md` 6.1절이 소유한다.

세 조건은 모두 지켰다 — `user_id`는 인증 세션에서만 도출하고, `confirm` 기본값 `false`로 첫 호출은 항상 주문 없는 프리뷰이며, 실행 경로는 사용자 작업 락과 심볼 주문 락을 모두 경유한다.

설계에 없던 문제가 하나 있었다. **티커 하나가 여러 슬라이스에 대응할 수 있다** — 1단계에서 같은 종목을 봇 슬롯과 `EXTERNAL`로 동시에 보유할 수 있게 만들었기 때문이다. 임의로 하나를 고르면 사용자가 의도하지 않은 슬라이스를 파는 사고가 되므로, 후보가 둘 이상이면 `400`으로 거절하고 후보 목록(수량·관할권)을 돌려준 뒤 `strategy_type` 지정을 요구한다.

전량 청산과의 중복은 `_sell_holding_slice`로 합쳤다. 주문 인텐트 생성·제출·정산(ACK_UNKNOWN 포함)과 실현손익·수수료 계산이 매도 경로마다 복제되면 한쪽만 고쳐지는 순간 금액이 갈리기 때문이다. 심볼 락은 헬퍼가 아니라 호출자가 잡는다 — 락 실패의 응답 코드가 맥락마다 달라야 한다(전량 청산은 중단, 개별 매도는 409).

**관할권은 봇의 자율 매도를 가르는 값이지 사용자의 수동 매도를 막지 않는다.** `EXTERNAL`도 사용자가 직접 지시하면 팔린다. 이것이 격리 계약의 나머지 절반이다.

## 9. 모바일 연동

수확 모드의 전제가 "사용자가 자고 있다"는 것이므로, 그 시간에 닿는 채널이 중요하다.

### 9.1 알림 채널 — 텔레그램이 먼저다 (2026-09-06 정정)

당초 "모바일 푸시가 주 채널"로 적었으나 **백엔드에 푸시 인프라가 존재하지 않는다.** 전수 확인 결과 FCM·디바이스 토큰·`/devices/register` 어느 것도 저장소에 없고(`app/main.py`의 라우터 등록 15개에 해당 항목 없음), 현재 유일한 알림 채널은 텔레그램이다. 모바일 앱에는 클라이언트 측 `registerDevice()`가 있으나 받아줄 서버가 없다.

따라서 순서를 이렇게 고정한다.

- **3~4단계 알림은 텔레그램으로 낸다.** 이미 사용자 휴대폰에 도달하고 2026-09-02 슬라이스에서 전달이 실증됐다. 수확·방어 기능이 FCM 구축을 기다릴 이유가 없다.
- **FCM 푸시는 별도 트랙**이다. 3~4단계의 선행 조건이 아니라 이후의 채널 업그레이드로 다룬다.

### 9.2 모바일 사전점검 결과 (stock-auto-mobile 회신, 2026-09-06)

- **Holdings 화면 자체가 없다.** 대시보드 잔고 카드는 집계값만 보여주고 종목별 행이 없으며, `getHoldings()`도 `Holding` 타입도 없다. 관심종목 탭은 감시 종목이라 재사용 불가. **모드 UI·개별 매도·상태 필드가 전부 여기 걸리므로 Holdings 뷰가 모바일 측 선행 과제다.**
- **푸시 권한 흐름은 갖춰져 있다.** 다만 포그라운드 수신 시 표시가 없고(현재 로그만), 알림 탭 딥링크가 없으며, 서버가 없어 관통선이 미검증이다. 9.1의 결론과 합치면 이 셋은 FCM 트랙으로 함께 미룬다.
- **375px 과밀 우려.** 모드 UI를 행에 인라인으로 넣지 말고 종목 상세 바텀시트로 빼되 행에는 배지만 노출하는 것을 모바일이 제안했다. 화면 구성은 모바일 세션의 판단에 맡긴다.
- **개별 매도는 강한 확인 시트**(수량·예상가)와 중복 탭 가드가 필요하다. 2단계의 confirm 게이트와 같은 요구이므로 계약에 함께 넣는다.

### 9.3 필드 계약 — 지금 확정할 것과 미룰 것

모바일이 `management_mode: "none"|"partial"|"full"` + `harvest_on_surge`/`alert_on_crash` 불리언을 조기 고정하자고 제안했다. 축이 둘로 나뉘므로 이렇게 정리한다.

- **`management`(확정, 1단계 구현 완료)** — 저장·판정의 단일 권한. `BOT_OWNED` / `EXTERNAL`, 뒤에 `DELEGATED` 추가. 봇이 산 것인지 사용자가 산 것인지의 구분이며, 모바일이 요청한 "봇 매수분 구분 플래그"가 곧 이 필드다. 별도 플래그를 추가하지 않는다.
- **사용자 대면 모드(미확정, 3단계 이후)** — 화면의 라디오는 파생값이다. `BOT_OWNED`는 선택지 없이 "봇 관리 중" 고정, `EXTERNAL`+스위치 전부 꺼짐이 "맡기지 않음", 스위치 하나라도 켜지면 "부분적으로 맡김", `DELEGATED`가 "봇에 전부 맡김"이다.
- **지금 `management_mode`를 노출하지 않는 이유**: 1단계에는 스위치가 없어 `"partial"`이 발생할 수 없는 값이다. 존재하지 않는 동작의 계약을 먼저 내보내면 모바일이 만들 수 없는 UI를 만들게 된다. 스위치가 실제로 생기는 3단계에서 파생 필드를 함께 확정한다.
- **FCM `data.type`**(`harvest_armed` / `harvest_filled` / `defense_alert`) 요청은 타당하다. FCM 트랙 착수 시 이 이름으로 고정한다.

계약이 확정된 범위(1단계)는 `API_STANDARD.md` 6절이 소유하며, 그 밖의 범위는 해당 단계 착수 시 통지한다.
