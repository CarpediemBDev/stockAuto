# 🚨 StockAuto 아키텍처 개편 계획서(v2) 까칠한 보안 및 로직 감사 보고서

본 문서는 `AGENTS.md`에 의거하여 **"가장 까칠한 보안 및 로직 감사관 (Critical Auditor)"**의 관점에서 v2 개편 계획서의 기술적 맹점, 비동기 레이스 조건, 소수점/자본 고갈 오차, 성능 병목 등 **터질 수 있는 치명적인 구멍 4가지**를 집요하게 파헤친 비판적 감사 보고서입니다.

---

## 📌 [구멍 1] 비동기 팬아웃 캐시의 레이스 컨디션 (Race Condition)
*   **원인**: 다중 유저·전략의 API 호출 폭증을 막기 위해 `루프 스코프 내 인메모리 캐시`(`{ticker: 결과}`)를 둔다고 설계했습니다. 그러나 현재 스케줄러는 `asyncio.gather(*tasks)`로 **모든 활성 유저의 트레이딩 루프를 동시에 완전히 비동기(Concurrent)로 실행**합니다.
*   **동작 구멍**: 
    1. 유저 A와 유저 B의 루프가 동시에 도는 순간, 동일 티커 `NVDA`에 대해 둘 다 캐시 미스(Cache Miss)가 발생합니다.
    2. 동시성 제어 락(Lock)이 없기 때문에, 유저 A와 유저 B의 태스크가 **거의 동시에 yfinance 및 Gemini AI API를 각자 호출**하게 되어 중복 제거 캐시가 무력화됩니다.
*   **비판적 제안**: 티커 단위로 비동기 락을 관리하는 `asyncio.Lock` 풀(Pool) 또는 세마포어를 설계에 명시하지 않으면, 다중 유저 실거래 상황에서 API 차단 방어막은 무참히 파괴될 것입니다.

## 📌 [구멍 2] CPU 연산 오버헤드: `inspect.signature` 리플렉션 병목
*   **원인**: 500개 종목 × 유저 수 × 슬롯 수(예: 3슬롯)로 루프가 확장되면서 1분 내 연산 지연 리스크를 언급했으나, 그 원인이 되는 치명적인 파이썬 코드 병목을 놓쳤습니다.
*   **동작 구멍**: 
    *   현재 채점기 다리 역할을 하는 `scanner.py:105`의 `calculate_strategy_score` 함수는 다음과 같이 구현되어 있습니다:
        ```python
        params = inspect.signature(strategy_instance.calculate_score).parameters
        ```
    *   파이썬의 `inspect.signature`는 런타임에 클래스 메타데이터를 역추적하는 **엄청나게 느린 리플렉션(Reflection) 연산**입니다. 이를 500개 종목을 도는 실시간 루프에서 매번 호출하면 CPU 점유율이 폭증하며, 1분 루프는 높은 확률로 시간 초과(Timeout)되어 먹통이 됩니다.
*   **비판적 제안**: 전략 생성 시점에 `has_score_card`와 같은 불리언 플래그를 미리 캐싱해두거나, `inspect` 호출을 완전히 제거하는 경량화 설계가 계획서에 반드시 포함되어야 합니다.

## 📌 [구멍 3] 전단 채점(Stage 1) 단계의 데이터 누락으로 인한 런타임 Crash (KeyError/NoneType)
*   **원인**: 뉴스 분석과 재무제표 스크래핑을 2단계 동적 정밀 분석(후단)으로 보류하고, 1단계에서는 오직 시세/기술 지표만 가지고 500개 종목 전체에 대해 유저 전략의 `calculate_score`를 돌린다고 설계했습니다.
*   **동작 구멍**:
    *   94개 전략 중 일부(예: `strategy_c.py` 등)는 채점 로직 한가운데에서 뉴스 감성 지수(`news_sentiment_score`)나 흑자 여부(`is_fundamental_healthy`)를 직접 참조하여 덧셈/뺄셈 연산을 하도록 짜여 있습니다.
    *   전단 스코어링 시점에 이 데이터가 None이거나 존재하지 않으면, 전략 내부에서 `KeyError` 또는 `TypeError: unsupported operand type(s) for +: 'NoneType' and 'float'` 에러가 터져 **스케줄러 루프 전체가 Crash로 중단**되는 치명적인 결함이 발생합니다.
*   **비판적 제안**: 전략 채점 메서드가 "뉴스/재무가 아직 수집되지 않은 1차 스코어링 상태"임을 인지하고 안전하게 Fallback값(예: 0.0 또는 기본 가중치)을 사용하도록 매개변수를 확장하거나 안전 장치를 걸어야 합니다.

## 📌 [구멍 4] 자금 선점 레이스 콘디션에 의한 "엘리트 종목 탈락" (Capital Starvation)
*   **원인**: v2에서 `get_focused_tickers`를 전략 후단으로 이동하여 500개 중 컷오프를 통과한 종목들 사이에서 최종 focusing을 적용하겠다고 했습니다.
*   **동작 구멍**:
    *   컷오프를 통과한 종목 A(점수 98점)와 종목 B(점수 86점)가 있다고 가정합니다.
    *   두 종목이 비동기적으로 뉴스/Gemini API 검증 파이프라인에 진입하는데, **종목 B의 API 응답이 네트워크 지연 차이로 먼저 도착**합니다.
    *   B가 먼저 매수 처리되면서 유저의 예수금이 바닥나고, 뒤늦게 API 검증을 마친 진짜 우수한 종목 A는 **예수금 부족**으로 매수되지 못하고 탈락합니다.
*   **비판적 제안**: 비동기 API 요청이 완료될 때까지 대기했다가, 최종 후보들의 점수를 정렬하여 **예수금을 우선순위(점수) 내림차순으로 할당 및 집행하는 동기화 조율 로직**이 배정되어야 합니다.
