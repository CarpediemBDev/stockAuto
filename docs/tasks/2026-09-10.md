- 생산자: backend/app/trades/router_trades.py(GET /trades에 ticker 쿼리 파라미터·normalize_ticker 신설), frontend/components/HoldingHistory.tsx(신규 - 종목별 체결 이력 뷰와 슬라이스별 보유 시작 계산), frontend/components/PortfolioView.tsx(티커 버튼·푸터 이력 버튼·이력 모달 배선), frontend/components/TradeLogs.tsx(TradeLog 타입에 strategy_type·signal_score·regime_mode 추가), locales/ko.json·locales/en.json(portfolio.history_* 19키 신설), backend/tests/test_trade_log_ticker_filter.py(신규 5건), frontend/e2e/holding-history.spec.ts(신규 1건)
- 소비자: GET /api/v1/trades(기존 소비자는 대시보드 전체 로그·리포트 페이지로 둘 다 ticker 없이 호출해 영향 없음), 프론트 포트폴리오 카드, 모바일 앱(stock-auto-mobile - 선택적 파라미터라 통지 없이도 호환되며, 종목별 이력 화면을 만들 때 쓸 수 있다)
- 데이터 경계: 읽기 전용이다. 테이블·컬럼 추가 없고 쓰기 경로를 건드리지 않는다. 조회는 종전대로 user_id로 먼저 좁힌 뒤 ticker를 걸어 사용자 격리가 필터 유무와 무관하게 유지된다. 티커 표기는 대문자화와 거래소 접두 제거로 정규화하되 저장 정본(접두 없는 대문자 심볼)은 바꾸지 않는다. 프런트는 한 번에 최근 500건까지만 받으며, 보유 시작 시각은 그 창 안에서만 계산되고 창에 닿으면 화면이 그 사실을 명시한다.
- API 계약: GET /api/v1/trades에 선택적 쿼리 파라미터 ticker가 추가된다. 필터는 DB에서 limit보다 먼저 적용되며 skip·limit은 필터된 결과 위에서 동작한다 - 전체를 받아 화면에서 거르는 방식과 결과가 다르고, 그 차이가 이 변경의 핵심이다(거래가 잦은 종목에 밀려 조용한 보유분의 매수 기록이 응답 창 밖으로 나가던 문제). 공백만 전달되면 필터를 걸지 않고 전체를 반환한다. 티커를 주지 않는 기존 호출의 동작은 완전히 동일하다.
- 문서 반영: docs/API_STANDARD.md 7절 "거래 원장 조회 계약" 신설(필터 적용 순서, 티커 정규화, 사용자 격리, 응답 항목, 빈 배열의 의미, 포지션 시작 시각을 서버가 계산하지 않는다는 계약).
- 회귀 테스트: backend/tests/test_trade_log_ticker_filter.py 5건 - 필터가 limit보다 먼저 걸릴 것(활발한 종목 150건에 밀린 매수 1건을 찾아내고, 필터 없이 부르면 그 행이 없음을 네거티브 대조로 확인), 사용자 격리 유지, 표기 정규화(AAPL·nas_aapl·NAS_AAPL·공백 포함), 티커 미지정 시 종전 계약 유지, skip/limit이 필터 위에서 동작할 것. 네거티브 컨트롤로 필터 한 줄을 무력화하자 5건 중 4건이 실패했고(남은 1건은 티커 미지정 계약이라 영향받지 않는 것이 정상) 되돌리니 전부 통과했다. frontend/e2e/holding-history.spec.ts 1건 - 클릭이 ticker=QLD를 실어 보내는지, 체결가·시각이 렌더되는지, 팔았다 다시 산 종목의 보유 시작이 첫 매수가 아니라 재진입 시점인지. python scripts/verify_harness.py 8/8 통과 - pytest 583건, tsc, eslint, Playwright 9건. 중간 2회는 다른 세션이 같은 체크아웃에서 하네스를 동시에 돌려 BLOCKED이었다(1회차 `.next-e2e` 빌드 락 충돌로 웹서버 기동 실패, 2회차 auth-smoke의 refresh 대기 30초 타임아웃). 그 세션 종료를 기다려 직렬화하자 동일 트리에서 전부 통과했다 - 코드 문제가 아니라 실행 경합이다.
- 미해결 위험: 첫째, 실행 중인 백엔드(PID 22256, 2026-09-10 02:47 기동)는 이 변경 이전 코드라 재기동 전까지 ticker 파라미터를 무시하고 전 종목 최신 100건을 돌려준다. FastAPI가 모르는 쿼리 파라미터를 조용히 버리므로 화면은 오류 없이 다른 종목 이력을 섞어 보여준다 - 이 상태가 가장 위험한 오독 경로다. run.py의 reload는 하드코딩 False이고 라이브 A/B 계정이 매매 중이라 재기동 시점은 사용자 판단이 필요하다. 둘째, 보유 시작 계산은 조회 창(500건) 안에서만 유효하다. 창을 넘긴 종목은 "표시 범위 밖"으로 표기되며 잘못된 날짜를 지어내지 않지만, 답을 주지도 못한다. 셋째, 위임(DELEGATED) 전환은 holdings의 strategy_type을 바꾸지만 과거 trade_logs 행의 strategy_type은 그대로다. 위임 전후 체결이 서로 다른 슬라이스로 갈라져 보이며, 이는 원장이 실제로 그렇게 기록된 것이라 화면이 합치지 않는 편이 정직하다. 넷째, 시각 표기가 UI 언어와 무관하게 ko-KR 형식으로 찍힌다 - 기존 TradeLogs와 동일한 동작을 따른 것이라 이 변경의 회귀는 아니지만 영어 UI에서는 어색하다.
