- 회귀 테스트: python scripts/verify_harness.py 8/8 전체 통과. test_rate_limiter.py 9건 통과. 인계 전 상태를 믿지 않고 네거티브 컨트롤로 실증했다 - login에서 peer_max_requests=30을 빼자 신설 테스트가 같은 IP의 6번째 사용자에서 429로 실패했고(assert 429 != 429), 복원하니 통과했다. 즉 수정 전에는 공용 IP 뒤 6번째 사용자부터 로그인이 막히고 있었다. 사용자당 상한이 느슨해지지 않았는지도 같은 테스트가 단언한다 - 동일 사용자명 6회째는 여전히 429다. 최초 네거티브 컨트롤은 router.py에 peer_max_requests가 signup과 login 두 곳에 있어 첫 번째(signup, 이미 main에 병합됨)만 지우는 바람에 통과해버렸고, login 줄을 정확히 지목해 다시 확인했다
- 미해결 위험: IP당 상한이 5에서 30으로 올라가므로 한 IP에서 여러 계정을 훑는 스프레이 공격의 분당 시도 횟수가 6배가 된다. 단일 계정 브루트포스는 사용자당 5회 그대로라 영향이 없다. 계정 잠금(5회 실패 시)이 여전히 최종 방어선이며, 이 완화는 가용성과 공격 표면의 의도된 교환이다. 또한 test_api_integration.py의 폴백 윈도우 초기화는 Redis 장애 시 프로세스 전역 딕셔너리가 테스트 간 누수되는 것을 막는 위생 조치인데, 원래의 실패를 본 세션이 직접 재현하지는 않았다. Playwright 타임아웃 상향도 콜드 빌드가 180초를 넘길 수 있다는 근거에 따른 여유 확보이며 타임아웃 실패를 직접 재현하지는 않았다
- 인수인계: RateLimiter는 IP 키와 주체 키 두 개를 각각 검사한다. peer_max_requests를 주지 않으면 IP 키 한도가 max_requests로 떨어져 두 한도가 같아지고, 그 순간 공용 IP 전체가 한 계정 몫으로 묶인다. 계정 단위 방어를 조이려고 max_requests를 낮출 때마다 IP 한도가 함께 조여지는 구조이므로, 앞으로 key_field를 쓰는 엔드포인트를 추가하면 peer_max_requests를 반드시 함께 지정한다. 신설 테스트가 login 배선을 고정하므로 값을 빼면 즉시 반려된다. 이 코드 슬라이스도 다른 세션이 워킹트리에 남긴 미커밋 작업을 본 세션이 검증·인계한 것이라 서명이 실제 작성자와 다르다
