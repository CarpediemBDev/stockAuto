## 🔍 "트집 잡기" 검수 결과 리포트 (Critical Auditor Report)

### 1. [QA-5] Telegram ThreadPoolExecutor 및 Fallback 검증
- **구현 특징**:
  - `_poll_global_updates_loop`에서 전역 `_telegram_executor` (ThreadPoolExecutor, max_workers=5)에 `_process_global_message` 연산을 위임하여 텔레그램 롱폴링 루프 및 메인 이벤트 루프의 블로킹을 성공적으로 격리함.
  - `/status` 조회 시 KIS API 장애/타임아웃(Exception)이 일어나더라도 최신 `AccountEquitySnapshot` 정보를 DB에서 가져오도록 Fallback 구현함.
- **트집 잡기(오동작 시나리오 및 개선 필요점)**:
  - **DB 커넥션 풀 고갈 위험**: `_process_global_message`에서 `db = SessionLocal()`을 열고, 내부의 `_process_command`에서 다시 `db = SessionLocal()`을 별도로 열어서 닫고 있음. 유저 한 명이 명령어를 보낼 때마다 커넥션이 중첩적으로 소비되므로, 여러 사용자가 동시 명령어를 보낼 경우 풀이 빠르게 말라버릴 수 있음. (하나의 세션을 주입하는 구조로 개선할 필요 있음)
  - **자산 스냅샷의 타임스탬프 누락**: 폴백 안내 메시지 발송 시 이 스냅샷이 *언제* 캡처된 것인지 `captured_at` 시간을 알려주지 않아 투자자가 오래된 데이터를 최신 데이터로 오인할 위험이 있음.

### 2. [QA-6] Redis Lock Lease Renewal 및 Shield Release 검증
- **구현 특징**:
  - `locks.release()` 연산에 `asyncio.shield`를 씌워 부모 태스크가 취소(CancelledError)되더라도 Redis 상의 락 해제 스크립트 실행이 끝까지 완료되도록 하여 락 누수를 방지함.
  - `_renew_loop` 내에서 `RedisLockUnavailable` 예외 발생 시 최대 3회 exponential backoff + jitter 재시도를 수행함.
- **트집 잡기(오동작 시나리오 및 개선 필요점)**:
  - **재시도 대기 도중 TTL 만료 위험**: 만약 사용자가 짧은 락 TTL(예: 3~5초)을 인가한 경우, exponential backoff 대기 시간(1회차 0.5s, 2회차 1.0s, 3회차 2.0s 등)의 합이 TTL을 초과하여 락이 자동으로 릴리즈되어 동시성 가드가 뚫릴 수 있음.
  - **`asyncio.shield` 무한 블로킹**: `_do_release` 내부의 Redis 호출이 네트워크 타임아웃 없이 무한 대기할 경우 shield된 태스크가 취소되지 않고 영구히 백그라운드에 상주하여 리소스 누수가 유발될 수 있음.

### 3. [QA-7] SQLite Bootstrap FileLock 검증
- **구현 특징**:
  - Uvicorn/스케줄러 기동 시 SQLite 마이그레이션 DDL 중복 실행으로 인한 DB 락 고착을 방지하고자 `sqlite_migration.lock` 파일 락을 획득하도록 serializing 함.
- **트집 잡기(오동작 시나리오 및 개선 필요점)**:
  - **좀비 인스턴스의 Lock 독점**: 마이그레이션 수행 중 프로세스가 비정상 좀비 상태로 유지된다면 타 인스턴스들은 60초 타임아웃 이후 줄줄이 크래시(RuntimeError)가 나 서버가 영구 중단됨.
