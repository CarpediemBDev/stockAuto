# StockAuto AI 연속 작업 프로토콜

이 문서는 작업자가 바뀌어도 변경 의도, 데이터 경계, 검증 상태가 끊기지 않도록 하는 실행 절차의 SSOT입니다. 최상위 권한은 프로젝트 루트의 `AGENTS.md`에 있으며, 이 문서는 그 규칙을 실제 작업 형식으로 구체화합니다.

## 0. 공통/전용 레이어

- 공통 AI 작업 방식은 프로젝트 내부 `skills/common-ai-workflow/SKILL.md`를 기준으로 합니다.
- 이 문서는 StockAuto 전용 적용본입니다. StockAuto의 경로, 도메인 구조, 하네스, 거래 모드, 브로커, 금융 계산, 스캐너 데이터 경계만 이 문서에 둡니다.
- StockAuto 작업 중에는 `C:\Users\Im\.codex\skills` 아래 개인 설치본을 원본으로 읽거나 수정하지 않습니다.
- 새 프로젝트를 만들 때는 `skills/common-ai-workflow`를 복사해 공통 원칙을 먼저 적용하고, 이 문서의 StockAuto 전용 경로와 명령어를 그대로 복사하지 않습니다.

## 1. 문서 우선순위

충돌이 있으면 아래 순서로 판단합니다.

1. 런타임 system/developer 지침
2. `skills/common-ai-workflow/SKILL.md`: 모든 프로젝트에 재사용할 공통 AI 작업 원칙 및 Zero-Complacency 까칠한 감사관 추론 프로토콜
3. `AGENTS.md`: StockAuto 절대 규칙과 승인·Git 통제 및 도메인 정밀 검증 수칙
4. `docs/tasks/YYYY-MM-DD.md`: 당일 작업 일지, 현재 작업 상태와 사용자 승인 여부
5. 연결된 GitHub Issue 또는 Linear 이슈: GitHub는 버그 기술 원장, Linear는 중요 장기 작업과 우선순위
6. 도메인 계약 문서: 데이터 흐름, API, 스키마, 전략 규칙
7. 실제 코드와 테스트: 현재 구현 사실

문서와 코드가 다르면 코드를 그대로 정답으로 간주하지 않습니다. 차이를 현황판과 연결 이슈에 기록하고 어떤 계약이 맞는지 확인한 뒤 함께 정렬합니다.

## 2. 새 AI 시작 절차

1. 루트 `AGENTS.md`를 전체 확인합니다.
2. `docs/tasks/`에서 최신 일자 파일과 최근 `[/]`, `[ ]` 항목을 확인합니다.
3. 작업 항목에 연결된 GitHub/Linear 이슈를 확인합니다. 도구가 없으면 동기화됐다고 가정하지 않습니다.
4. 조회용 `git status`로 기존 사용자 변경과 미추적 파일을 확인합니다.
5. 변경할 파일, 호출자, 소비자, 테스트, 관련 문서를 실제 검색으로 확인합니다.
6. 신규 작업을 당일 현황판에 `[ ]`로 선등록하고 실제 시작 시 `[/]`로 전환합니다.
7. 아래 `변경 영향 기록`을 먼저 작성한 뒤 구현합니다.

신규 기능 구현 또는 기존 기능 확장 시에는 구현 전에 동일·유사 기능을 먼저 검색합니다. 같은 검증, DB 변경, API 호출, 캐시 갱신, 토스트 처리, 수수료·손익·수량 계산이 이미 있으면 새로 복사하지 말고 기존 원장 모듈을 확장하거나 원장 모듈을 새로 정한 뒤 모든 소비자가 그곳을 호출하게 합니다.

## 3. 계약 영향 변경 판정

다음 중 하나라도 바뀌면 계약 영향 변경입니다.

- API 경로, HTTP 메서드, 인증, 권한, 요청·응답 필드
- 사용자별 데이터와 공용 데이터의 분리 또는 재결합
- 전역 캐시, 캐시 키, 무효화, 백그라운드 갱신 방식
- 스케줄러 주기, 중복 실행 가드, 재시도·재개 조건
- DB 모델, 마이그레이션, 기본값, 데이터 보존 정책
- 외부 증권사·데이터 공급자 계약 또는 실패 폴백
- 프론트엔드가 의존하는 상태·폴링·에러 처리 계약
- 검증 하네스, CI, 배포 또는 운영 절차 (120% 고도화 검증: check_chaos_fuzzing 및 auto_rollback_guard 연동)

## 4. 변경 영향 기록 형식

계약 영향 변경 시 당일 현황판에 아래 블록을 그대로 사용합니다. 각 값은 실제 파일·함수·API·테스트 이름으로 작성하며 `없음`, `해당 없음`만 적지 않습니다.

```markdown
### 변경 영향 기록
- 변경 분류: `데이터 흐름`, `API 계약`
- 생산자: `backend/app/...`의 `function_name`
- 소비자: `/api/...`, `scheduler job`, `frontend/components/...`
- 데이터 경계: 공용 데이터와 `user_id` 기준 개인 데이터의 결합 위치
- API 계약: 인증, 입력, 출력, 오류, 비동기 상태의 변경 내용
- 문서 반영: `docs/...` 또는 `영향 없음 - 구체적인 사유`
- 회귀 테스트: 생산자 단위 테스트와 실제 소비 경로 통합 테스트
- 미해결 위험: 남은 위험과 추적 이슈 번호
- 인수인계: 다음 작업자가 처음 열 파일과 시작할 항목
```

## 6. 단계별 멀티 에이전트 파이프라인 (Multi-Agent Pipeline)

메인 에이전트가 작업을 수행할 때는 업무의 신뢰도와 예외 방지를 위해 아래 세 단계에 걸쳐 멀티 에이전트 협업 파이프라인을 기동해야 합니다.

1.  **[분석 단계] Codebase Researcher 가동**
    *   **시점**: 신규 코딩을 시작하기 전, 현황판 `docs/tasks/YYYY-MM-DD.md`에 작업을 `[/]`(진행 중)로 등록한 직후.
    *   **수행 내용**: `define_subagent` 및 `invoke_subagent`를 사용하여 `research` 에이전트를 가동하고, 중복 비즈니스 로직(SSOT) 유무와 소비자 영향도 맵을 도출해 마크다운으로 보고받습니다.
2.  **[구현 후 검수 단계] Critical Auditor 가동**
    *   **시점**: 소스코드 구현이 끝난 직후, 로컬 검증을 실행하기 전.
    *   **수행 내용**: `critical_auditor` 에이전트를 정의 및 호출하여, 변경된 소스코드에서 발견될 수 있는 엣지 케이스, 소수점 오차, 예외 누락 등 3개 이상의 핵심 위험 사항을 진단받고 이를 수정 보완합니다.
3.  **[최종 검증 단계] QA & Harness 가동**
    *   **시점**: 구현 및 자체/감사관 피드백 반영이 모두 완료된 후, 유저에게 최종 승인(`[R]`)을 요청하기 직전.
    *   **수행 내용**: `qa_harness` 에이전트를 소환해 `python -m py_compile`, `npm run lint`, `npx tsc --noEmit` 정적 분석 및 `scripts/check_chaos_fuzzing.py` 등 120% 고도화 검증 명령어를 기동하여 오류 0건을 입증하게 합니다.

이 3단계 파이프라인의 수행 내역 및 각 에이전트의 검증 보고서는 일자별 현황판(`docs/tasks/YYYY-MM-DD.md`) 혹은 인수인계 섹션에 간략히 요약하여 기록을 보존합니다.

## 7. 원격 반영 라이프사이클 (참조)

Git 라이프사이클의 **정본은 [`AGENTS.md`](../AGENTS.md) §2(Git 동결)·§2-1(브랜치 전략 및 6단계 라이프사이클)** 입니다. 이 문서가 소유하는 주제는 `docs/README.md`가 규정한 대로 "작업 시작·검증·인수인계 절차"이므로, 절차 본문을 여기 중복 기재하지 않습니다. 두 벌로 관리하면 트리거 정지선 같은 안전 규칙이 한쪽만 갱신돼 갈라집니다.

요약만 남깁니다 — AI는 Git 상태 변경을 자율 실행하지 않으며, 트리거마다 도달 지점이 다릅니다.

| 트리거 | 정지선 |
|---|---|
| `"로컬 커밋만 해줘"` | 2단계 (브랜치 생성·원자적 커밋) |
| `"커밋하자"` / `"깃에 올리자"` | 4단계 (PR 상정·CI 대기) — **병합하지 않음** |
| `"머지까지 진행해"` | 6단계 완결 (병합·브랜치 정리) |

단독 `"진행해"`로는 병합·브랜치 삭제 같은 비가역 원격 작업을 실행하지 않으며, 푸시·병합·원격 브랜치 삭제 직전에는 반드시 보고합니다. 각 단계의 정확한 명령과 저장소 설정 제약(`allow_auto_merge: false`)은 `AGENTS.md` §2-1을 따릅니다.
